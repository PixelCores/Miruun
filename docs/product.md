# Miruun 产品说明

> 本文保留用户提供的产品需求与历史交付状态。项目初始化后的构建、测试和验收事实见 [VALIDATION.md](../VALIDATION.md)。

文档日期：2026 年 10 月 2 日

对应源码：Miruun 0.3.1

产品阶段：实验性原生 macOS 工具，纯 Swift 源码已交付，尚待 Mac 编译与运行验收

## 1 产品概述

**Miruun 是一个面向 Codex 桌面工作流的 macOS 菜单栏工具，目标是在用户切换已授权的模型服务接入方式后，仍能回到原来的对话继续工作。**

它围绕一个具体动作设计：选中已有对话与已配置的目标 provider，核对身份和风险，完成本机备份，通过原生后端重新绑定该对话的服务路由，再检查绑定是否保留。用户无需手动导出历史、整理摘要、导入新聊天或创建分支。

产品的核心价值是减少长期任务因接入方式变化而中断的成本。实现上必须同时维护原对话身份、原模型与项目关联，并明确区分“后端设置已验证”和“用户已经在原 GUI 中成功续聊”。当前版本采用退出客户端后执行的保守流程；原窗口完全不关闭的热切换属于后续探索。

## 2 项目缘起与要解决的问题

Miruun 源于一次真实的使用需求：用户先通过自己的 ChatGPT 账户在 Codex GUI 中建立了一段持续工作的对话，之后希望通过 CC Switch 与 CLIProxyAPI，使用另一条已授权接入路径继续完成任务。

当时，新建的自定义 provider 对话可以正常使用，原对话却仍向 `api.openai.com` 发起请求，并出现 401 与 bearer 认证相关错误。更换全局配置或在界面中看到新的模型标签，并没有保证原对话的实际请求路由已经变化。

排查表明，该问题涉及原线程持久化的 provider 设置及恢复时的设置重放。只复制会话文件，或只修改目录索引、文件头中的 provider，可能仍被旧运行时设置覆盖。公开问题记录也描述了相近现象，但这些报告只能作为机制参考，不能证明每个 401 都有相同原因。[CC Switch #5672](https://github.com/farion1231/cc-switch/issues/5672)、[CC Switch #5922](https://github.com/farion1231/cc-switch/issues/5922)

最初的导出与重新导入方案没有满足需求：用户要延续的是原来的工作线程，而不仅是让另一段新聊天看到一份历史文本。因此，产品方向转为“保留原 ID，通过原生接口重新绑定，再验证”。

早期处理流程已经在一个具体用户案例中实现原对话续聊，并获得用户确认及 CLIProxyAPI 对应请求返回 200 的辅助证据。这证明了该案例的可行性，仍需与新的 Swift 产品实现分开评价。

## 3 面向谁与典型场景

Miruun 优先服务以下用户：

- 使用 macOS 上的 Codex GUI，已在同一对话中积累项目背景、约束、工具记录与工作进度的人
- 已自行配置并获得授权使用不同 provider 或代理接入路径，希望切换后继续原任务的人
- 遇到“新对话正常、原对话仍走旧地址”的路由不一致问题，需要可核对处理流程的人

典型场景包括：长期代码分析中更换接入服务、既有代理配置调整后恢复原项目线程，以及对疑似失效的 provider 绑定进行检查。

使用前提是目标接入本身有效、原模型在目标服务可用，并且用户接受把相关内容发送给该服务。Miruun 不提供账户、额度、独立账户池或代理服务，也不绕过登录与权限限制。账户选择、认证和计费归属仍由现有接入配置及其上游系统负责。

## 4 原对话连续性的定义

对 Miruun 而言，连续性首先意味着：**同一个线程 ID、同一个项目、保留原模型，并回到同一条 GUI 对话继续任务。** 不能以新建、fork 或粘贴摘要替代这一验收标准。

具体产品原则如下：

1. **先认准对象。** 标题、完整 ID、项目目录和模型共同参与核对，不能只凭列表位置或相似标题决定目标。
2. **变更范围可见。** 一次确认只对应一个原线程和一个目标 provider，不扩展为批量迁移。
3. **使用原生恢复路径。** 优先调用安装在本机的后端协议，不把直接重写历史文件当作切换完成。
4. **保留证据，谨慎报告。** 缺少通知、出现超时或读到元数据，都不能独立判定最终结果。

“延续上下文”是用户体验目标，不等于保证模型永久记住全部历史。上下文压缩、不同服务的模型实现、工具能力和后端版本仍可能影响实际接续效果。当前也没有承诺把一个账户的云端聊天资产迁移到另一个账户。

## 5 用户操作流程

原有问题流程是：切换配置 → 返回原对话 → 请求仍走旧路由 → 反复尝试、复制内容或重新开始。

Miruun 的目标流程是：

1. 在原 GUI 中核对目标对话，正常退出所有相关客户端与其他后端。
2. 从菜单栏打开 Miruun，选择实际安装的 ChatGPT／Codex 后端及对应数据目录。
3. 读取对话与 provider 目录，按标题搜索并选中原对话。
4. 选择已配置的目标 provider，并在接入配置中独立核对真实地址。
5. 独立选择预期项目目录，运行预检；身份、状态或版本不符时停止。
6. 在确认面板核对完整 ID、标题、项目、保留模型、目标地址及备份与联网风险。
7. 确认后执行本机备份和原线程恢复，再用独立后端进程检查持久化结果。
8. 得到明确结果后重新打开原对话，由用户主动续聊，确认任务背景与实际路由。

这里的“一次操作”指工具承接备份、恢复与验证流程，不意味着省略确认，也不代表后台持续替用户切换账户。应用不会强制结束用户的客户端。

## 6 核心功能范围

下表描述当前源码中的实现范围，运行可信度见第 9 节。

| 功能           | 产品行为与边界                                               |
| -------------- | ------------------------------------------------------------ |
| 应用与后端发现 | 扫描候选应用信息，允许手动选择；不靠应用显示名硬编码路径，不自动执行未选中的候选程序 |
| 对话查找       | 展示有限的 ID、真实标题、项目、时间、模型与 provider 元数据；支持标题搜索和单独查询归档对话，不读取完整历史作为列表预览 |
| Provider 目录  | 从选定数据目录的配置读取候选项，仅显示脱敏地址来源；无法安全解析的 TOML 或不明确目标会被拒绝 |
| 精确预检       | 核对线程身份、项目、模型、后端版本与协议、客户端关闭状态、队列及相关自动执行功能状态 |
| 单次确认       | 绑定精确线程、provider、地址与配置版本；确认限时且只能使用一次，执行前再次检查 |
| 本机备份       | 备份选中会话记录及共享 SQLite 状态库，使用 SQLite backup API 包含已提交 WAL 数据；备份可能涉及其他线程元数据 |
| 原线程重绑定   | 调用原生 `thread/resume`，显式指定目标 provider 与原模型，要求响应保持原 ID |
| 独立进程验证   | 关闭变更后端，再以新进程、不带 provider／模型覆盖地恢复，检查目标设置是否仍然生效 |
| 异常记录与锁定 | 保存本机回执与未决标记；不确定结果进入只读状态，不自动重试、回滚或另建线程 |

只读复核只报告存储元数据，不会再次恢复线程，也不能替代实际路由证明或自动解除未决锁。后端可能对相同设置通知去重，因此源码已避免把“未收到重复通知”直接当作失败。

## 7 实现结构与依赖关系

产品采用原生菜单栏界面与本机安全引擎分离的结构。当前源码使用 **Swift 与 AppKit**，引擎使用 Foundation、CryptoKit 和系统 SQLite3；没有 Python 构建或运行依赖，也没有 WebView、网页服务或第三方 Swift 包依赖。

界面负责选择、风险展示和操作状态；引擎负责预检、备份、原生 RPC、独立进程验证与回执。实际 Codex 后端来自用户已安装的桌面应用，Miruun 不替换整个聊天客户端。

原生同线程恢复的接口依据可见于 [Codex App Server 官方文档](https://learn.chatgpt.com/docs/app-server)。具体版本的持久化行为还须按源码审查与运行验收确认，不能只凭接口名称推断兼容性。

当前构建要求 macOS 13+、Swift 5.9+ 与相应 macOS SDK。桌面应用名称与内嵌后端版本可能不同，应分别发现和核对。CC Switch 或其他配置工具后续再次改写配置，也可能影响已经验证过的路由。

## 8 隐私与风险边界

Miruun 本身不读取或改写 `auth.json`，不管理账户登录，也不把备份与回执自动上传或云同步。但本机后端启动时可能读取自己的认证配置、维护缓存或联网；“本机工具”不等于整个流程完全离线。

即使没有主动发出用户回合，恢复、预热及验证仍可能向配置的供应商或 MCP 服务发送基础指令、工具元数据，并发生认证或初始化请求，可能产生费用。后续主动续聊还可能发送历史内容。确认界面必须明确说明这些目的与接收方范围，不能承诺零网络、零请求或零费用。

备份中既有选定对话，也可能含其他对话的私人元数据或排队消息，应按私人数据保存在本机受限目录。工具不会自动清理备份或回滚共享数据库，以免覆盖其他状态。

版本未知、队列非空、功能状态无法确认、目标地址不清楚、文件结构异常或结果不确定时，应停止写入并保留证据。强制退出后仍需保留未决状态；不能通过删除锁文件来把不确定操作当作全新请求。

## 10 成功标准

一次完整的产品验收至少需要满足：

- 操作对象与用户确认一致，原线程 ID、项目目录和原模型保持正确
- 目标 provider 与地址经核对，独立后端冷重开仍返回预期设置
- GUI 打开的是原对话，没有通过新建、导入或 fork 替代
- 用户主动发送后得到可用回复，并确认先前任务背景得到接续
- 对应实际请求到达预期服务路径；不能仅靠模型标签、元数据或单个 HTTP 200 判断
- 未静默改动登录、凭据或其他线程，未引入未经确认的数据发送
- 失败或不确定时保留备份和证据，不把重复尝试包装成成功

后端验证通过只是上述证据链的一部分。具体上游账户与计费归属需要接入服务提供相应证据，不能由 provider 名称推断。

## 11 后续路线建议

以下是按风险与依赖排序的建议，没有承诺日期。

**第一阶段：完成原生闭环验收。** 在 Mac 上运行全部 Swift 测试与编译，先验证合成数据，再经明确同意验证真实原对话；覆盖超时、异常通知、并发客户端、崩溃重开与共享数据库备份。

**第二阶段：形成可分发版本。** 完成界面与可访问性检查、图标转换验证、签名公证、安装体验及清晰的支持版本范围。对不支持的环境给出可理解的停止原因。

**第三阶段：提高诊断可解释性。** 更清楚地呈现配置目标、有效设置与实际请求路径之间的差异，降低误选和误判；所有新增诊断都应重新评估数据与联网范围。

**后续探索：减少中断。** 研究在后端明确支持且风险可控时，缩短退出与重开的流程，逐步评估不关闭原窗口的切换。热切换、任意跨供应商上下文兼容和自动账户轮换目前均不属于已实现承诺。

## 12 名称与视觉方向

应用名为 **Miruun**，品牌展示可使用 **MIRUUN**。它是受 Mineru 启发、与 Eruun 的 `-uun` 音节呼应的原创名称，延续对《塞尔达传说》的喜爱。Nintendo 将 Mineru 介绍为魂之贤者；“承载方式改变，仍延续同一份精神”的联想被用于表达本产品的上下文连续性。[Nintendo 角色介绍](https://www.nintendo.com/us/amiibo/detail/minerus-construct-the-legend-of-zelda-tears-of-the-kingdom-series/)

[Eruun](https://github.com/PixelCores/Eruun) 与 Miruun 具有命名家族上的呼应，两者产品职责独立。这里不推定 Eruun 的词源，也不把 Miruun 描述为游戏中的官方词汇、官方合作项目或已经完成商标核查的名称。

图标采用深林绿底、玉色与象牙色交织的原创连续符文，表达流向切换时仍保持连贯。菜单栏使用适应明暗模式的小尺寸单色符号。已选定图标母版；最终 ICNS、Finder 与 Dock 的显示效果仍须在 Mac 上验证。

本文以本次产品讨论、0.3.1 源码说明及验证清单为依据。公开链接用于解释相关机制与命名背景；产品状态以明确列出的验证结果为准。
