# Miruun 产品说明

文档日期：2026 年 10 月 5 日。对应源码：Miruun 0.4.1、已合并的 `custom` 历史接入修复与启动前准备入口，以及未发布的毛玻璃界面简化；源码版本未变。产品阶段：实验性原生 macOS 菜单栏工具；实际构建、测试与运行验收见 [VALIDATION.md](../VALIDATION.md)。

## 产品目标

**Miruun 的目标是安静地在后台维护 Codex 的接入配置，让用户切换已授权的接入路径后，继续原来的对话，无需逐条选择、迁移或确认。**

用户只需选择实际使用的数据目录并启用一次守护，之后仍按原有方式使用 CC Switch 与本机代理。Miruun 在应用运行期间定期检查配置，识别受支持的本机 Responses/API Key 接入，保留原生 `openai` provider 标识，并把完整代理地址写入 `openai_base_url`。通过 Miruun 打开 Codex 时，先重新检查并准备配置，再启动使用所选 `CODEX_HOME` 的 Codex，省去手动等待状态这一步。

当前实现维护这个数据目录中**原生 `openai` 本地历史的接入**，并在切回官方 ChatGPT/OAuth 登录后补齐缺失的 `custom` provider 定义。旧历史仍保留原 provider ID；守护不扫描历史来逐条改写，也不新建、导入或 fork 对话。其他 provider ID、其他数据目录及云端账户资产不在当前覆盖范围。

后台维护配置已经成为当前产品流程；早期 0.3.1 的“选中单个线程，退出客户端，再恢复和验证”设计仅作为研究与初始化历史保留，详见 [代码分析](analysis.md)。

## 问题与实现依据

Miruun 源于一个长期任务的接续需求：用户通过自己的 ChatGPT 账户在 Codex GUI 中建立原对话，之后希望通过 CC Switch 与 CLIProxyAPI，使用另一条已授权接入路径继续工作。新建的自定义 provider 对话能够使用，旧对话却仍恢复此前的 provider，出现路由与认证错误。

Codex 0.159.2 的版本化源码显示，恢复旧对话时会读取持久化的模型与 provider ID，再从当前配置中查找这个 ID 对应的 provider 定义。将全局 `model_provider` 换成另一个 ID，不能保证原生 `openai` 历史随之换路由。线程保存的是 ID，不是一份独立的完整 endpoint 与认证配置。

因此，对于原生 `openai` 历史，较小的方案是保留这个标识，通过 Codex 支持的顶层 `openai_base_url` 指向本机代理。代理负责选择其已经授权的上游，Miruun 不增加账户池、另一套会话存储或聊天客户端。具体源码依据及边界见 [代码分析](analysis.md)。

反向切换也有同一类问题：停用 CC Switch + CLIProxyAPI、恢复账号 A 的官方登录后，`custom` 定义可能被移除，但旧历史仍保存 `custom` ID，导致 `Model provider custom not found`。本次修复补齐该 ID 的配置定义，使冷恢复能够解析当前官方认证入口；不需要改写历史。

## 使用流程

1. 通过现有接入工具配置可用的本机 Responses 代理和 API Key 登录。
2. 点击菜单栏月球图标，在浮窗“设置”中选择实际使用的 `CODEX_HOME`，返回概览开启守护。
3. 正常退出 Codex GUI 及其他 Codex 后端，点击浮窗概览的主要按钮“打开 Codex”。Miruun 等待连续稳定采样，按需备份原配置与认证、接入既有代理 Key，再维护 `model_provider = "openai"` 和完整的 `openai_base_url`。
4. 检查就绪或保存完成后，Miruun 自动启动 Codex GUI，使用所选数据目录；回到原对话主动续聊。
5. 后续照常切换接入；需要调整客户端配置时仍先退出 Codex。正常状态仅在菜单栏中显示；无法安全处理时显示具体原因并停止此次写入。
6. 停用代理、切回账号 A 时，先恢复官方 `openai` 入口及文件 ChatGPT/OAuth 登录，再退出 Codex 并通过 Miruun 打开；守护补齐缺失的 `custom` 定义并清理自己管理的本机地址，然后启动 Codex。

“打开 Codex”仅在守护启用时可用；每次请求使用新的检查结果，待配置稳定或客户端退出期间保持等待，不强制关闭已有任务。重复点击合并，失败显示原因；暂停或退出取消尚未发出的启动。守护每两秒在串行队列中检查一次，暂停或退出会等待正在进行的检查结束，再停止后续维护。关闭 Miruun 后不另留独立守护进程。

启动前还会以继承所选目录的登录 shell 预检 `CODEX_HOME`，识别固定目录覆盖；无法确认或不匹配时停止，不读取完整环境或显示 shell 输出。预检后重新检查配置和客户端；检查结束后至少等两秒再采样。按启动位置、父进程或命令分支的 shell 配置仍需单独验收。

可在概览开启“自动打开”，并从 Finder 将 `Miruun.app` 固定到 Dock。守护启用时，之后手动启动或再次打开 Miruun 都直接进入相同的准备流程，启动出错时打开完整状态子页；自动打开关闭或守护暂停时显示浮窗。系统登录项启动仍静默。直接启动原 Codex 不经过此入口，不能保证配置先准备完成。模式只由当前配置与认证决定，不把代理离线当作切回官方登录的指令，也不恢复旧 OAuth 备份。

菜单栏月球按钮打开带顶部箭头的半透明毛玻璃浮窗。概览只有守护和自动打开两行开关、一处实际状态入口，以及主要“打开 Codex”按钮；底部保留设置和退出。设置子页包含目录选择、备份和登录启动，底部“返回”回到概览；完整状态可以滚动查看并选择复制文字。

再次点击月球按钮、按 Esc 或点击其他应用仅收起浮窗，守护和待启动请求继续运行；后台状态更新不会反复展开界面。`⌘,` 打开设置，`⌘Q` 或“退出”结束应用，仍串行等待当前检查完成并取消尚未发出的启动。

配置文件变化不能保证已经运行的 GUI 或活动线程立即采用新路由及认证。长期使用固定本机代理地址、在代理内调整上游，可以减少客户端配置变化；活动请求和连接是否平滑接续，仍取决于客户端与代理的运行行为。

## 当前支持条件

| 条件 | 当前行为 |
| --- | --- |
| 原历史 provider | 原生 `openai` 历史共用 builtin 定义；`custom` 历史在官方文件 OAuth 下补齐缺失定义，无需逐条处理；其他 ID 不自动修复 |
| 代理地址 | 明确的 `127.0.0.1`、`localhost` 或 `[::1]` HTTP/HTTPS 地址；保留端口与完整路径，拒绝 URL 用户信息、查询及片段 |
| 目标自定义 provider | `base_url` 明确；支持 `requires_openai_auth = true` 配合文件 API Key，或 false 配合明确 inline bearer；`wire_api` 省略或为 `"responses"` |
| 认证 | 支持文件 API Key；也支持当前自定义 provider 通过 `experimental_bearer_token` 提供 Key，并在备份后转为 Codex API Key 文件认证 |
| 凭据存储 | 默认文件存储或明确 `cli_auth_credentials_store = "file"`；不猜测 keyring、auto 或 ephemeral 中的认证 |
| 配置覆盖 | 包含 profile 或已知登录覆盖时停止；外部 CLI、host 或受管理配置的实际优先级仍需运行验收 |
| 特殊 provider 设置 | 自定义认证、请求头、查询参数和其他额外 provider 字段无法只靠复制地址保留，当前停止处理 |
| ChatGPT/OAuth 登录 | 当前选中受支持的 inline bearer provider 时，备份后转换为 API Key；官方 `openai` 模式下撤销本工具标记的代理地址、补齐缺失的 `custom` 定义，不改凭据 |
| `custom` 定义 | 已有未标记定义保留；工具创建的定义随有效原生入口同步；被修改、含额外字段或非本机地址时停止；无法安全追加的 inline table 不改写 |

`openai` 是 Codex 的保留 provider ID，不能依靠 `[model_providers.openai]` 覆盖它。守护使用顶层 `openai_base_url`，不会把 endpoint 简化为仅有 origin 的地址。原模型配置及其他 TOML 内容、表和注释均保留。

补齐 `custom` 的条件是根 `model_provider` 为 `openai` 或省略、文件认证为 ChatGPT/OAuth，且该定义缺失。新增定义带 `# miruun-managed-custom-provider` 标记，使用 `name = "OpenAI"`、Responses 和 OpenAI 认证。OAuth 下省略 `base_url`，由 Codex 选择官方 ChatGPT 入口；不把 OAuth 凭据发送到旧代理。之后切回受支持的本机 API Key 接入时，已管理定义的 `base_url` 跟随完整 `openai_base_url`，回到 OAuth 时再次删除该地址。它默认使用 HTTP SSE，不承诺 builtin `openai` 的 WebSocket 能力。

启用守护表示允许将当前代理接入统一为 Codex API Key 模式，原有文件认证先备份。Miruun 不校验代理内最终选中了哪个上游账户。它采用 builtin `openai` 的传输与能力设置；仅复制地址不能证明任意自定义 provider 的行为完全等价。

## 数据与安全

启用后，Miruun 读取选定目录的 `config.toml` 与可选的 `auth.json`。接管当前 provider 自带的代理 Key 时，会在备份后将认证写为 Codex API Key 模式，并维护原生入口；所有写入等待客户端与后端退出。它不记录或显示 API Key，不读取会话内容或 SQLite。后台检查不启动 Codex；授权的启动入口通过系统打开 `com.openai.codex`，传入相同 `CODEX_HOME`，不直接运行或修改内嵌后端，也不替用户发送回合。

写入前保存私有配置备份，使用受限权限的文件、完整写入与同步，再进行原子替换。备份保存原配置以及原认证（若存在），认证原本不存在时保存缺失记录；这些文件包含敏感信息，目录 0700、文件 0600，只留本机。

守护拒绝链接、非普通文件、所有权异常、超限数据和无法安全解析的 TOML。连续两次相同采样及保存前再次比较用于发现已有变化，但原子 rename 不是跨程序的 compare-and-swap；不合作的配置工具仍可能在最终检查之后写入。配置与认证文件分别提交也不是整体原子事务；提交阶段出错会保留备份并停止自动重试。通过启动入口重新打开 GUI 前，应先完成 CC Switch 切换，停止其他正在写配置的操作。

发生冲突、备份失败或持久化结果不明时，状态中显示原因并保留已产生的备份，不自动回滚。开始提交前的失败可在后续稳定配置下重新检查；开始提交后则保留按数据目录区分的未决记录，重开应用也停止自动重试。不会把旧备份强行覆盖到新的配置之上。

Miruun 本身不进行接入联网。用户在 Codex 中续聊时，实际客户端与代理会按照生效配置处理请求，可能发送历史内容并产生费用，接收方、授权和计费由现有接入负责。

## 连续性与验收边界

产品目标中的连续性意味着回到同一个原对话，保留原 ID、项目关联与本地历史；是否正确加载背景，还需要原 GUI 中的实际回复验证。

当前源码验证与公开机制分析支持“维护原生入口并补齐缺失的 `custom` 定义”，尚未证明所有原对话均能在任意账户、模型或供应商之间无中断接续。Codex 0.159.2 的 `thread/list` 默认按当前 provider 筛选，只有显式空 `modelProviders` 才包含所有 provider；补齐定义不保证 GUI 会显示全部 `custom` 历史。Codex 的会话路由还可能保持在内存中；CLIProxyAPI 的 WebSocket 增量请求依赖连接与所选认证，账号变化可能要求重连和完整重放。加密 reasoning、压缩历史和工具状态的跨接入兼容性不能从配置结果推断。

完整运行验收应分别核对：

- 启用后，连续切换与应用重开均能维护预期入口，配置、注释及模型未意外变化。
- 多个原生 `openai` 原对话仍保持各自 ID、项目与历史，并能在原 GUI 中主动续聊。
- 停用代理回到账号 A 后，旧 `custom` 原对话可打开并使用官方认证续聊；再启用代理时，同一历史跟随受支持的本机入口。
- 实际请求到达预期本机代理；最终上游账户需代理提供独立证据。
- OAuth、特殊认证、文件冲突和不支持的配置都按边界处理，没有泄露凭据或覆盖新配置。
- GUI 重启、活动请求、WebSocket 重连、压缩和工具调用分别获得运行证据。

0.4.1 开发未读取真实私人会话或数据库；当时为排查故障只读检查了本机配置和认证文件是否存在，代理 Key 仅在内存中用于本机模型列表检查，未发送真实续聊请求；另在隔离数据目录中使用实际 Codex 后端和合成凭据、历史完成冷恢复验证。2026-10-03 的修复在合成环境复现了缺失 `custom` 的错误，补齐定义后以同一 ID 冷恢复，并在切回 mock 代理后重放历史。修复已通过 PR #1 合并，用户重启后确认回到账号 A 可以继续 `custom` 历史对话；该反馈不代表完整 A → B → A、全部历史或新启动入口已通过实机验收。具体证据以 [VALIDATION.md](../VALIDATION.md) 为准；签名、公证与洁净机器分发仍是独立验收项。

## 实现与后续方向

应用使用 Swift、AppKit 和 Foundation，已有研究引擎还使用 CryptoKit 与系统 SQLite3，没有第三方 Swift 包或 Python 运行依赖。当前菜单栏浮窗直接调用配置守护，界面收起不改变后台调度；早期原生恢复引擎保留为研究实现，不在后台流程中运行。

后续首先验证原生 `openai` 多对话、`custom` 历史回到官方账号再切回代理、真实 CC Switch 写入时序、固定入口下的代理上游切换与 GUI 重载。只有实际协议与运行证据支持后，才扩大到更多历史 provider 或减少重启步骤；不把修改历史文件当作通用迁移承诺。

## 名称与视觉

应用名为 **Miruun**，品牌展示可用 **MIRUUN**。名称受 Mineru 启发，与 Eruun 的 `-uun` 音节呼应，表达承载方式变化后仍延续原有任务的联想。[Nintendo 的 Mineru 角色介绍](https://www.nintendo.com/us/amiibo/detail/minerus-construct-the-legend-of-zelda-tears-of-the-kingdom-series/)

原产品说明提出深林绿、玉色与象牙色的连续符文图标，源目录未包含该应用图标母版。当前菜单栏与浮窗使用绘制的单色月球 Logo，以一枚居中、略微倾斜的猫爪印代替月面凹坑，圆润的脚趾与肉垫以半透明层次呈现。浮窗为 332 × 350 pt 的原生毛玻璃表面，保留顶部箭头。半透明与背景融合由系统合成，随桌面内容变化，并遵循系统辅助功能设置。应用图标、签名与公证未由构建通过代替验收。
